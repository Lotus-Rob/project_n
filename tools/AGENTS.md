# tools/: build tooling

## Scope
`project_n.py` (the entry point, run as `pixi run project_n` or the root `dev`/`dev.cmd` wrappers), its tests, the Pixi activation script and the gdb init file.

## Rules
- `project_n.py` is one file, standard library only, and thin: commands call XMake, Podman, git, git-cliff, gh and the pinned tools; anything those tools do stays there.
- `dev` and `dev.cmd` only forward to `pixi run project_n`; behaviour belongs in project_n.py.
- `PRESETS`, `IMAGES` and `SCOPES` at the top of the file are the single source of truth. Changing a preset or scope updates design doc 0001 §3/§11 and any AGENTS.md that names it.
- Containers re-enter the same script (`reenter`): add behaviour once, not per environment.
- Never pipe XMake's output through filters; it stalled twice that way in spike S4.
- `env/activate.sh` runs on every `pixi run`: keep it fast and idempotent.
- `--help` is read by shell completers (lig): an option with choices opens its help with `[possible values: a, b]`, on one line because `help_format` doesn't wrap piped output; `test --list-tests [--suite S]` prints what `--test` takes.

## Commands
- `pixi run project_n selftest` runs the self-checks in `test_project_n.py` (no Podman needed); `check` runs them first.
- `pixi run project_n test --suite <s>` without `--test` or doctest arguments runs `xmake test <s>/*`: the suite's file tests (tests/AGENTS.md) in parallel; with them, `xmake run <s>` runs the binary once. A target that is no suite (`headless_bench`) always runs its binary.
- `pixi run project_n prune-worktrees`: removes worktrees under `.worktrees/` and `.claude/worktrees/` whose branch is gone from origin and whose changes are all in origin/main (`git cherry`, as a rebase merge rewrites commits), with their branches; keeps locked, detached or dirty ones, ones without commits of their own yet (just made, never pushed) and the checkout it runs in, and says why; a folder deleted by hand is reported, left to the closing `git worktree prune`, and its branch deleted after it if merged.
- `pixi run project_n setup`: once per clone (and per worktree), writes `CLONE_CONFIG` (the commit hooks, Git LFS's filters through `pixi run git-lfs`) into the local git config and fetches the LFS files (design doc 0001.1); `check` refuses a clone without it (`clone_set_up`).

## Skills
- git-commit (for `SCOPES` changes)

## Gotchas
- XMake's package cache ignores the compiler version: `packages_dir()` gives each `pixi.toml` + `pixi.lock` its own `XMAKE_PKG_INSTALLDIR`, on every host (so not in the Linux-only activation script). `project_n clean --packages` removes old ones, `clean --images` stale container images.
- `xmake f` runs with `-v` on purpose: it serialises package installs. In parallel, XMake installs duplicate variants with one build hash (libxcb, libx11 via SDL3) into the same directory and they corrupt each other ("install: ... No such file or directory").
- The env's gdb reads `$CONDA_PREFIX/etc/gdbinit`, which the gdb package already uses; `env/activate.sh` appends a single `source` line for `debug/gdbinit` rather than replacing the file.
- XMake rewrites `xmake-requires.lock` on every call: in another order (`__meta__` moves, entries swap: Lua table order), and with only the entries the current configuration uses (the windows-msvc container drops native Windows' meson, pkgconf and python entries from `windows|x64`: its own host tools lock under `linux|x86_64`, which holds meson and python 3.x but no pkgconf). `run` writes the old bytes back after every XMake call, failed ones too, when it only reordered or dropped entries, compared entry by entry (`restore_lock_unless_added`, `lock_entries`); call XMake only through `run`; an added or changed entry (versions, hashes, a platform's missing entries) stays and prints its diff: commit it then. So removing a dependency leaves its entries until deleted by hand (add-dependency skill). CI's macos and windows jobs are the only `macosx|arm64` and native `windows|x64` hosts, so their logs carry that diff: the `macosx|arm64` entries of five requires added from Linux were missing, so each macOS job added them and its caches never hit (2026-11-13). `artifact` and `release` still ignore the lock in their clean-tree check.

- On Windows, `subprocess` decodes output with the locale (cp1252) and crashes on XMake's UTF-8; `capture()` forces UTF-8. Running a program by bare name finds only `.exe` files (conda's xmake is `xmake.cmd`); `run()`/`capture()` resolve it through `shutil.which`. For xmake they skip the shim entirely: its trailing `endlocal` turns every exit code into 0, so failed tests passed CI.
- MSVC `C1382` ("the PCH file has been rebuilt since ...obj") after a package's include paths change: XMake rebuilt the PCH but not the objects using it. `pixi run project_n clean --preset windows-msvc` and build again.
- msvc-wine's `bin/x64/cl.exe` is our `CL_WRAPPER` (`install_cl_wrapper`, from `ensure_msvc`), and `xmake.lua` turns XMake's build cache off for MSVC off Windows unless its `build_cache` option is set (`project_n` sets it only for `CI_CACHED_TOOLCHAINS`, which leave msvc out): under Wine the `/sourceDependencies` JSON XMake asks cl for names headers as lowercased `z:\…` paths it can't find, so every windows-msvc build recompiled all 143 files, twice per `check` (107 s; 5 s with nothing changed now, 2026-11-12). The wrapper drops that option only when `PROJECT_N_CL_DROP_SOURCE_DEPENDENCIES=1` (`xmake_env` sets it): the install is shared by every checkout, and one whose `xmake.lua` keeps the cache on needs the option, so without the variable it passes everything through. Dropped, XMake reads `/showIncludes`, which msvc-wine's `cl` turns into Linux paths; the build cache compiles the preprocessed file, whose `/showIncludes` lists no headers. A header change rebuilds exactly its includers.
- XMake's compile database export turns packages' `-isystem` into `-I` unless given `--lsp=clangd` (`COMPDB`); without it clangd and `lint` report warnings in third-party headers and their macros as ours.
- Git LFS runs from git itself, in any git (an editor's, a container's), so its filters must name `pixi run git-lfs`, never a bare `git-lfs` the host may lack or have at another version. `lint` checks committed pointers (`check_lfs_pointers`, `git lfs fsck --pointers`); `artifact` refuses pointer files in `assets/` (`lfs_pointers`).
- XMake takes an ancestor folder holding a project (one with `.xmake/`) over the current directory, so in a worktree under `.claude/worktrees/` it built the main checkout ("You are working in the project directory(...)"). `resolve()` passes `-P <ROOT>` to every XMake task; `XMAKE_PROJECT_DIR` doesn't work. Run XMake through `project_n`, never bare, in a worktree.
- A worktree outside the repo fails to check out ("smudge filter lfs failed": the filter runs `pixi run git-lfs` in the new folder before its `pixi.toml` exists; `GIT_LFS_SKIP_SMUDGE` doesn't help, the filter process can't start). Inside the repo Pixi finds the main checkout's `pixi.toml` further up.
- No compile cache is shared between checkouts, on purpose: XMake compiles our sources through its built-in cache (Clang only: never GCC, below; XMake skips `cl` on Windows, and MSVC under Wine is off, above), per build directory, and hands only package builds to an installed ccache. A shared `--ccachedir` hit 0 of 140 compiles from another worktree (2026-11-14): XMake's key (`cachekey`) holds the compiler's path and the preprocessed text, both naming the worktree (its own `.pixi`; the precompiled headers' headers, which `-E` names by absolute path, no flag mapping them), and `-ffile-prefix-map=<ROOT>=.` can't help, as XMake keys on the flag's text. A Pixi env shared by every worktree, a plain `-include` for each PCH and `-ffile-compilation-dir=.` hit 128 of 140, byte-identical to a cold compile: a fresh worktree's linux-clang debug build in 9 s instead of 20 s, but every cold one in 28 s. Not taken: an architecture change, and dropping the PCH changes shipped builds' compile flags (only path-mapping flags may). Cold builds (XMake's time, 2026-11-14, 32 shared cores): linux-clang debug 20 s, release 35 s, releasedbg 43 s, linux-gcc release 64 s, windows-msvc release 53 s; the packages are shared through `packages_dir()`.
- CI's object cache: XMake turns its build cache off when it sees CI, so with `PROJECT_N_BUILD_CACHE=<dir>` set (`BUILD_CACHE_ENV`; CI's workflow keeps the folder with actions/cache) `configure` passes `--build_cache=y` (xmake.lua's project policy, which XMake reads before its CI switch) and `--ccachedir=<dir>/<preset>-<leaf>` (`object_cache_dir`), outside the build folder so `artifact`'s clean room keeps it; containers get it mounted at `/home/dev/build-cache` with `GITHUB_REF`. Only `CI_CACHED_TOOLCHAINS` (pixi-clang): GCC never uses the build cache (below), and msvc-wine's is off (above). The cold rule (`cold_ref`: main or a tag): a build writes only into an empty cache folder, creating it when absent, and otherwise (`PROJECT_N_BUILD_CACHE` unset, a non-empty folder, a tag, which uses none, or an uncached toolchain) passes `--ccache=n`, so XMake's own cache in the build folder (on in containers, which see no `CI`) stays off; it refuses a build folder that already holds objects in `.objs/` or a leftover `.build_cache/` (`holds_objects`). Unset (locally) nothing changes.
- `xmake.lua` turns XMake's build cache off for `pixi-gcc` everywhere, and `build_cache` can't turn it back on: XMake preprocesses with `-fpch-preprocess`, whose text holds `#pragma GCC pch_preprocess "<pch>.gch"` instead of the precompiled header's headers, and keys each object on that text, so after a change to `core/types.hpp` a linux-gcc build handed back the old object and a test still saw the old value (2026-11-13). Clang's text holds those headers.
- `lint` runs one clang-tidy per unit across all cores (`tidy_units`), as many at once as this process may use (`jobs()`: affinity and cpusets count), not one process over every unit (5.5 min serial, 33 s parallel on 32 cores, 2026-11-10) and not `run-clang-tidy`: its exit code is 1 if any file fails, so a file erroring without a finding beside files with only ignored findings would pass. Each unit is judged by `tidy_verdict` alone. `--fix` then runs one serial `clang-tidy --fix` over the units that failed (`tidy_fix`): exporting fixes and applying them with `clang-apply-replacements` (as `run-clang-tidy -fix` does) also applies note fix-its that only silence a warning (`static_cast` around a widening multiply), which plain `--fix` never does. A shared header's finding prints once, compared by resolved path (clang-tidy spells it `./src/…`, `src/…` or absolute depending on the unit); an ignored (listed) one never prints and is counted once the same way. Each unit's result (output and exit code) is kept as `<key>.json` in `tidy_cache_dir` (`<PROJECT_N_BUILD_CACHE>/tidy` in CI, saved by the object cache's steps; else the build folder's `.tidy-cache`) and a hit prints exactly what the run printed; `tidy_key` hashes, per compile database entry (sorted: XMake exports a file two targets compile, `tests/unit/gfx/main.cpp`, either way round), its flags without input and output, its `-E` text and the bytes of every repo file that text's line markers name (`-E` drops comments, so a NOLINT edit would otherwise hit), plus `clang-tidy --version`, the arguments lint passes it (`tidy_command`, the build folder and unit as placeholders) and every `.clang-tidy`. The cold rule holds: main and tags read none (main stores its results, a tag nothing); a crash or a unit that fails to preprocess, or has no compile database entry (the three fuzz targets), is never cached. Measured 2026-11-13 (141 units, 32 cores): 84 s cold, 13 s with every result kept (keys cost ~12 s: one `-E` per unit). Its units are the changed `.cpp` files and those whose XMake records (`.deps/**/*.o.d`, fresh after lint's own build: `unit_dependencies`; XMake never deletes one, so only units in the build's fresh compile database count) name a changed file; a unit without a record (the fuzz targets, which lint's build skips) is always linted, and a changed header no record names is reported, not linted.
- `reference` runs each test case in its own process (`run_reference_case`, picked by position: some names hold commas, which `--test-case` splits on), `jobs()` at once: one process kept lavapipe on 1.4 of 32 cores, 28 s for 25 cases; in parallel they draw in 4 s (2026-11-12). Outputs print in case order after all finish, and a failing run ends with one line naming the failed cases. Each case gets its own `XDG_RUNTIME_DIR`: otherwise all of them make Mesa's fallback `/tmp/xdg-runtime-mesa-<uid>` at once and the loser crashes (main, 2026-11-13).
- Leave the tree alone while `check` runs: it lints and builds what is on disk at each step, so a file written meanwhile, or `shaders` rewriting `src/gfx/generated/shaders.hpp` before a build has made its `*.spv.h`, fails clang-tidy falsely, and a failure in one step hides the real ones after it.
- `doctor` exits 3 for "problems found", so CI can report them without hiding real errors (exit 1).
