# src/: game and engine

## Scope
All game and engine code, structured by docs/design/0002-engine-architecture.md (phases 1 to 5 of §16 implemented). Modules are XMake static libraries in `src/<module>/` (`core`, `data`, `platform`, `gfx`, `game`, `app` so far; `data` reads the YAML files, settings and data tables (which are hashed game data, which presentation, and the C++ defaults that mirror them, `game::BuiltInData()` and `core::Effects{}`: assets/AGENTS.md), into core's types, and only it sees yaml-cpp); each links and includes only the modules below it (`MODULES` in tools/project_n.py; `lint` checks the includes), and `game` links only `core`. `app` puts the program together (0002.1): `app::App` owns the job system and the main thread's systems (window, renderer, display, camera, damage numbers, HUD; the camera, `app::CameraControl`, moves as the snapshot's `core::CameraKind` says and starts afresh at each scene change) and runs the main loop; it starts the logic thread, which registers with the job system (only the creating thread and registered ones fork) and builds an `app::Game` owning that thread's systems (saves, `game::Host` through `core::Simulation`, `core::Logic`, the tick clock). The threads share only `core::GameHandover` (`core/frame.hpp`). Scenes load on demand (0002.3.1): each snapshot names the scene its state needs; App has the renderer decode and upload its sprites a little each frame, then sends `SceneResident`, and until then the logic's bursts wait, running no tick. Every scene change, the start, save loads and replay starts included, runs through stages the logic publishes (`Snapshot::sceneChange`: leaving, loading, entering, running), none of them ticking; App answers leaving and entering through `core::SceneReports` (at once until transitions are drawn). Each drawn frame App also sends its view (`GameHandover::SendView`: `core::ViewReport`, the window's world rectangle plus a margin from `app::CullArea`, named by `core::ShownChange`), a latest value that is never tick input (never recorded, hashed or saved): the host culls each publish to the latest view of the scene shown or, until one arrives (the start, after each swap, harnesses that send none), to the widest view a window shows (`core::WIDEST_HALF_VIEW`) round where the camera starts. `main.cpp` only parses the command line, reads the settings (`settings.yaml` in the per-user data folder: window size, fullscreen, language, text and damage number options, edge pan; `core/settings.hpp`), the atlas manifest, the game data and the strings table, opens the window and renderer (with the text options and the table of UI colours, `core::UiColours`: every UI colour lives there, none in code or shaders), and runs an `App`. `assets/data/effects.yaml` (`data::LoadEffects`, into `core::Effects`: not game data, so not hashed or saved) holds every presentation number: the swords', bolt's and burst's sizes, trails and glow, the health bars and the HUD's layout; debug builds' data watch reloads it on the main thread and hands it to `gfx::Renderer::SetEffects` and `app::Hud::SetEffects`, so a change shows the next frame and the simulation never knows. `assets/data/seals.yaml` (`data::LoadSeals`, into `core::Seals`, its sprites checked against the manifest: presentation too, not hashed or saved) holds each seal's look (plane, ink wash, colours, life, rings and their parts, emblem, satellites, light) by name; `main` reads it after the manifest, and the data watch reloads it like `effects.yaml` into `gfx::Renderer::SetSeals` (which packs its parts then, never on a first draw), keeping the old table on an error, while a seal key the table lacks is logged once and draws nothing; game data and the simulation name a seal only by its key (`core::SealKeyOf`). `assets/data/world.yaml` (`data::ParseWorldMap` / `LoadWorldMap`, into `core::WorldMap` through `WorldMap::Build`; besides the map it holds `profiles:` (at least one, `on_foot` first: `core::MovementProfile`, a pace in ticks per cost unit plus `all_kinds`, `kinds` and `features` overrides of the base costs), `travel:` (`core::TravelRules`: share, stay days, reach, the cultivator threshold) and each city's `draws:` per visitor kind (`core::Place::draws`, a danger's always 0), all hashed; each place's name looked up in the strings, each entry's yaml-cpp line kept in `WorldMapSource::lines` so refusals name it) is game data, hashed with the rest (`GameData::Hash` mixes in `world->Hash()`; null in `game::BuiltInData()`), read once at start after the strings and not reloaded: the data watch keeps the running map (`app::KeepWorld`), so a `world.yaml` edit alone changes nothing; a missing or broken one stops the game with its error. `assets/data/names.yaml` (`data::ParseNames` / `LoadNames`, into `core::Names`) is game data the same way (`GameData::names`, hashed through `names->Hash()`, null in `game::BuiltInData()`, read at start after the map, kept by `app::KeepWorld`): an NPC's name is never stored, only `core::NameOf(names, seed, id)` (a surname by weight, then one given character in 3 of 10 or two), shown as `core::NameText` in the language and stacked by `core::NameKey`: a label carries it as `TextItem::npcName` (its `string` ignored), `gfx::Renderer::SetNames` takes the table (App at start and after a data reload) and prewarms every glyph of it (`TextLayout::PrewarmNames`), and the renderer composes and measures each distinct name once a frame (`gfx::NameTexts`, `gfx::LabelKey`). `assets/data/world_look.yaml` (`data::ParseWorldLook` / `LoadWorldLook`, into `core::WorldLook`, its sprites checked against the manifest and the world scene's sprite list there, `data::WORLD_LOOK_SCENE`, so none draws from a page that isn't loaded, and its kinds and danger sorts against the loaded map: a kind or sort the map uses with no look or marker is refused, extras are accepted; presentation, never hashed, saved or seen by `game`) is read at start after the map, held in `app::Options::worldLook` and reloaded by the data watch on the main thread like `seals.yaml`, the old look kept (and logged) on an error; a broken one stops the game at start. What changes what happens (a sword's motion, the fight's times and the aura) is game data, in `abilities.yaml`. A new system is owned by `App` or `Game`, never passed in as loose arguments.

## Rules
- C++23 with conventional headers (no modules). Every translation unit's includes lead to `core/cxx23.hpp`, which fails the build below C++23; include it with `// IWYU pragma: keep` (it declares nothing).
- Include order: project headers, then library headers (`<SDL3/...>`), then (headers only) the standard library, as blank-line-separated blocks. clang-format sorts within a block but doesn't regroup.
- Formatting and lint come from the pinned tools: `pixi run project_n fmt` and `pixi run project_n lint` (warnings are errors).
- Headers include only the standard library and our own headers. Third-party and platform code (SDL, Tracy, `<windows.h>`) stays in `.cpp` files behind our own types (a pimpl or an opaque handle); a header doesn't forward-declare its types either. `lint` fails on a third-party include in a header; only a facade (`FACADES` in tools/project_n.py) includes its own library, and a module's private `src/<module>/internal/` headers its libraries (nothing outside the module includes them).
- Numbers use the sized types from `core/types.hpp`: `i8`–`i64`, `u8`–`u64`, `f32`, `f64`, never `int`, `unsigned`, `long`, `float`, `double` or `std::uint32_t`-style names (`int main(int, char**)` excepted; `std::size_t` stays for sizes and indices; `lint` fails on the others). `pch.hpp` includes it; headers include it themselves.
- `pch.hpp` is the game's precompiled header and holds every standard header the sources use: a `.cpp` never includes a standard header itself (`lint` fails on one); add it to `pch.hpp`. Headers still include everything they use. It is a header too: no third-party ones.
- Logging: extensive, through `core/log.hpp` (Quill; `std::format` syntax, written on a background thread). Log outcomes (what was chosen, what happened, what failed and why), never code steps or internals, and never every frame (profile instead). `main` calls `core::log::Start(directory)` first; logs go to the console (Info and up) and to a rotating `project_n.log` in the per-user data folder. Nothing else writes output (`std::print`, iostreams, `printf`, `SDL_Log`) and nothing else includes Quill or Tracy: `lint` fails on them. Levels:
  - `PN_LOG_DEBUG` detail for diagnosing (decisions, state changes, values; log file only)
  - `PN_LOG_INFO` progress in a normal run (subsystems starting and stopping, what was chosen)
  - `PN_LOG_NOTICE` significant normal events (start, stop)
  - `PN_LOG_WARNING` unexpected but recovered · `PN_LOG_ERROR` a failure and its cause · `PN_LOG_CRITICAL` a failure the program can't continue after
- Profiling: `PN_PROFILE_ZONE();` at the top of every function that runs each frame (except per-item functions: Gotchas), `PN_PROFILE_FRAME();` once per frame, from `core/profile.hpp` (Tracy). They collect only in `releasedbg` and do nothing elsewhere: `./dev profile [--seconds N] [-- --stress]` records a run into `build/profiles/` (the game quits by itself with `--quit-after N`, so no click into the viewer takes its focus and pauses it), `./dev profiler <file>` opens it; or live, `./dev run --mode releasedbg` and `./dev profiler`.
- Every header starts with a `/// @file` comment followed by `/// @ingroup <module>` (the group is in `src/<module>/module.dox`), and every public class, function, member, variable and enum it declares has a Doxygen comment (`///`): what it does and promises, not how. `lint` fails on a missing or broken one.
- Errors: an expected failure returns `std::expected<T, core::Error>` (`core/error.hpp`); a broken invariant is `PN_ASSERT(condition, message)` (`core/assert.hpp`: on in debug and releasedbg). Our code throws nothing.
- Entities: EnTT only through `core/ecs.hpp` (a facade; `core::Domain`, `core::Registry`). Anything that crosses a domain, a tick, a save or input names an entity by its `core::StableId`, never an EnTT handle; `core::State::Create` takes it from one of two ranges, both counters saved and never reused: the world's (`core::IdRange::World`, NPCs and groups, from 1, so a world generated from a seed numbers alike whatever ran before) and a scene's own (`IdRange::Scene`, from `core::SCENE_ID_BASE`, 2^62: the cultivator, creatures, a scene's props; one counter for the session, carried from scene to scene whichever world runs); structural changes (create, destroy) never happen inside a job chunk.
- Simulation code (`core`, `game`) is deterministic within one binary (design doc 0002 §7.4): transcendental maths through `core/math.hpp` (`lint` fails on `std::sin` and the like there), random numbers through `core/random.hpp` keyed on the state counter, never `std::*_distribution`, never a clock.
- Comments in `.cpp` files only explain why, or a complexity the code can't show; never restate what the code does. A comment directly above a function, method, lambda-holding variable or helper type that states its contract (what it returns or does, its inputs' ranges, its promises) is `///` Doxygen; one that only restates the body goes; a comment saying what a constant or data table holds is that constant's documentation and stays. No comment cites a spec, chunk, phase, plan, ruling, task or design doc (`lint` fails on one): say why in your own words.
- Rendering: the world pass first draws the world map when the snapshot shows it (`Snapshot::worldMap`, from `SceneTraits::worldMap`: only the world scene; the scene publishes no tiles and no painted ground; `gfx/terrain_draw.hpp` lays the tiles in view, the river and road overlays, bridges, fords and place markers out from the `core::WorldMap` and `core::WorldLook` given to `Renderer::SetWorld`, which App calls at start and whenever a look reload replaces the look; one more sprite buffer, laid out and copied again only when the view reaches other tiles or SetWorld is called; every instance flagged `core::INSTANCE_FOGGED_LAND`, which the sprite shader drains to sepia and veils in mist where its pixel's tile is explored but out of sight and shades in the look's shade colour where it is unexplored, by `View::fog` (`gfx::FogFrame`, `gfx/fog.hpp`) through `internal::FogTexture` (`gfx/internal/features/sprites.hpp`: a two-channel UNORM texture a texel per tile, explored and in sight, filtered linearly and clamped, uploaded only when its revision changes, bound to every sprite draw; with no fog a 1 × 1 one and nothing shaded), as an instance flagged `core::INSTANCE_SIGHT_FADE` fades with sight at its `core::SightPoint` and a label by `gfx::FogOpacity`, one wholly hidden taking no label room), then the player's route and the target cursor's tile (`gfx/route_draw.hpp`, another sprite buffer laid out each frame from `Snapshot::route` and `Renderer::SetTargetTile`: a `route_dot` every `route.spacing` units of `world_look.yaml`, `route_marker` on the end, `target_tile` on the cursor), then draws the snapshot's ground and decals (its first `Snapshot::groundBatches`, which the draw list cuts there), the ground seals (each its ink wash and its particles' ink, with the light shadows overhead seals cast on the ground, normal blend, then its lines and its light's pillars, sparks and shards, additive), the rest of the snapshot's sprites, the selection and hover outlines (the glows `selected` and `hover`, drawn alone round those sprites), the upright and overhead seals (drawn alike, their light with them, capped in opacity, under all that follows, so the swords fly out over them and health bars, numbers and the HUD stay readable; `gfx/seal_draw.hpp` lays every seal out at the render time from `Snapshot::seals`, `gfx/internal/features/seals.hpp` draws them), the swords' trails (additive ribbons), the overlay (sprites the main thread places each frame at the render time: the swords, each one instance wearing its glow, then the poison lance's additive bursts, then the health bars, which follow their creature's label and stay readable over the swords; `gfx/volley_draw.hpp`: the snapshot carries each volley as one record, `Snapshot::volleys` with their targets in `volleyTargets`, never a sword each, and every sword is placed by `core::SwordAt` at the exact render time), then text, then the HUD in target pixels (`app/hud.hpp` lays it out: its bars through the overlay's sprites, then its lines); on the world map it also lays out the date line (`Hud::BuildDate` from `Snapshot::calendar`: month and day counted from 1, "Paused" after it while the world is paused, right-aligned top right through `HudLine::alignRight`), whose box (`Hud::DateLineArea`, laid out by `hud.date_inset` in `effects.yaml`, as wide as the text draws, `gfx::Renderer::HudLineWidth`, and never narrower than `hud.date_width`) is the HUD's one clickable area: a primary mouse press in it sends `ToggleWorldPause` through `app::DateLineClick` and nothing else, ahead of the world's click). Nothing outside `gfx` calls SDL_GPU. Shaders are HLSL in `shaders/<name>.<stage>.hlsl`; after changing one, `./dev shaders` (Linux or Windows) and commit `shaders/bin/` and `src/gfx/generated/` with it (`lint` fails on stale binaries). `gfx` reaches them through the generated `gfx/generated/shaders.hpp`.
- Third-party code comes from xmake-repo packages with exact versions; nothing is vendored into `src/`.
- `src/<module>/generated/` holds headers that `shaders` and `atlas` write (shader binaries, the sprite names; the atlas manifest itself is `assets/manifest.yaml`, which `main` loads into `core::Manifest`): never edit them by hand; `fmt` and `lint` skip them, and `lint` fails when they are stale.
- The arena (`game/scenes/arena.hpp`) is the growing demo scene: a new feature of the game or engine shows up in it, in the same branch, and is added to the header's list. Each scene is a stateless class in `game/scenes/` behind `game/scene.hpp`, listed in `game/scenes.cpp` (F2's order; a scene's key is its place there, its constant in `game/scenes.hpp`, checked at compile time); its hooks add ground under the entities (`Scene::PublishGround`: the painted ground by default, none for a scene that shows the world map; culled to the publish's area by the scene itself, drawn whole) and content over them (`Scene::Publish`); the host (`game/host.hpp`) owns all state and never checks which scene it runs. It keeps the game's world (`game::WorldState`, `game/world_state.hpp`: the state, relationships, travel, calendar, pause, the cultivator's place on the map, the explored tiles and the sight radius), made once by `GenerateWorld` (the constructor, which keeps it as made, `Host`'s base, and runs a copy; a load makes the base again from the save's seed) and never rebuilt by a scene change: a game scene (today `world`) runs on it, and a dev scene (`SceneTraits::devScene`: arena, stress, painted, cells) on a scratch world made afresh on each entry (`BuildScratch`, through a `WorldContext`, the scene's way into a world; kept as made beside it for its saves, and after it is left, so re-entering it or loading a save of it shares that rather than building it again), with its own `worldNpcs` crowd and its own calendar (M there steps only it), the game's world set aside untouched (`Host::WorldHash()` hashes it alone; `StateHash` hashes the running world and the scene). A scene build clears the last scene from the game's world (the world NPCs it brought in back to the world domain by `Deactivate`, its own entities destroyed), and the scene-ID counter moves on into whichever world runs (`State::SetSceneIds`). Saves hold the game's world, then the scratch world while a dev scene runs, then the scene; the game's world as its difference from its base (the base's identity: seed, `GENERATOR_VERSION` and `GameData::BaseHash()`, the world map and names only, so an `abilities.yaml` or `creatures.yaml` edit orphans no save; a load of another generator or other world data is refused, logged saying which), the world domain by `core::SaveDomainDelta` and its order by `core::SaveDomainOrder` (a byte a storage while it keeps the base's order), the journeys by `Travel::SaveDelta` (the base's gone by place, the others by `core::PlanOf` when `core::Rebuild` gives them back exactly, else whole), relationships (each NPC's kept to `RELATIONSHIP_LENGTH`, or `MET_RELATIONSHIP_LENGTH` once met, the most recently met kept, trimmed by each month step), journals, the explored tiles and the sight radius whole; the scratch world likewise as its difference from its scene's entry build (made again by a load: a save names no seed for it), the scene whole. A save never sorts: it leaves the state as it runs, every storage's order included, and a load gives that order back, so a game that saves runs on as one that never did; `GenerateWorld` ends with `State::SortCanonical`. The world clock (`Host::WorldTicks()`, the running world's, saved and hashed: a day `TICKS_PER_DAY` ticks, core's `core::TICKS_PER_DAY` in `core/calendar.hpp`, which journeys count by too, a month `DAYS_PER_MONTH` days) moves a tick each tick only in a scene showing the world map and not paused (`core::ActionKind::ToggleWorldPause`, ignored elsewhere, kept by the game's world through other scenes; paused, the cultivator stands too), stands still at a month's end until the step (`Simulation::MonthDue()`, which the logic answers after a tick that ran as it does an `AdvanceCalendar`: transition, then the step), and is published there as `Snapshot::calendar` (months passed and day of the month); the world scene needs `GameData::world` (`CheckScenes` refuses it without, `main` checks after reading the map, `Host` asserts). The world scene places the cultivator where it last stood on the map (`WorldState::mapPlace`: the foot when F2 left it, the point before the step onto the portal when a portal did, so it never lands back on it; a place in the portal's step area, where M's jump can leave it, is never kept, nor loaded), on the map's start city in a new game or with no place kept, names every place in view (`core::TextKind::Place`, one per place with its own entity and name key, hung under the tile's marker so the cultivator's label on the start city stays clear). Its view is the map's size (`Scene::View(context)` for a scene that follows the game data, `SceneTraits::viewFromMap`, as `Scene::Portal` is for its portal; `Host::View()` gives the running scene's), what a publish culls round before a window's view arrives when no cultivator is followed. `GenerateWorld` spawns each city's `people` as world NPCs (`Npc::home`: the city's place index, `NO_HOME` in scenes without a map; `Npc::cell`: a map tile index there, the 64-column grid in the arena and stress), seven tenths on the city's tile, the rest on a drawn tile of its region, each with a starting `Npc::power` from `StartingPower(seed, id)` (80% in [0, 5), 18% in [5, 50), 2% in [50, 500); the arena and stress start at 0); `Host::Load` refuses an NPC whose home or tile doesn't suit its world (a scratch world's are homeless). The host also keeps the world's travel (`game::Travel` in `game/travel.hpp`, `Host::NpcTravel()`): the journeys under way as `core::Journey` records in their first members' order, a member's month `Action::Travel` until `Travel::Finish` ends its journey (the month step leaves such an NPC as it is and never makes it a partner; `Travel::LoadDelta` refuses a member whose month isn't `Action::Travel` and an NPC travelling on no journey), and each NPC's travel journal, its last `JOURNAL_LENGTH` journeys (`MET_JOURNAL_LENGTH` once met), written as each ends; saved with the world as its difference from the base's and hashed whole (the world section's `WORLD_VERSION`, 7), kept with the game's world across scene builds, and refused by `Host::Load` in a scratch world or a game without the world map. Each month step on the world map ends the journeys over by the clock's tick, then sends a share of the NPCs at home on visits (never one standing on a tile walkers can't enter, which its way back would have to step onto; `Travel::Month`, forked in `MonthStep::CHUNK` chunks and merged in chunk order, every draw keyed on the seed, the state counter, the month and the NPC: the destination weighed by `DestinationWeight`, pull, reach and the city's draw for the visitor's kind in whole numbers, the route walked from the NPC's own tile and back), then runs the month's actions; `GenerateWorld` seeds the travel of the month before the calendar's start and of its first (`Travel::Seed`, its chunks in turn as generation has no job system), so the roads are busy from the first frame. On the world map each publish draws every member of each journey under way at the clock whose foot is in the area as a villager with its shadow and its ID (pickable, selectable), placed by `core::Where` at the clock when the last tick began and at the clock now (a presentation-only copy of the clock, never saved: a load or a month step's jump sets it to the clock, so travellers stand still a frame rather than streak), packed in the publish's chunks after the entities' and merged in chunk order (the player's cultivator sorts after the whole world layer there, so the crowds on the cities' tiles never hide it), and labelled with its name (`TextItem::npcName` from `core::NameOf`, `LabelPriority::Named`, `Selected` when selected) when the game data has names. The host keeps the map's distance maps (`core::Paths`) for the run. On the world map a `core::ActionKind::WalkTo` (its point in `Action::point`, recorded in replays) lets go of the selection, wherever it points, and sets the player's cultivator on a route (`Host::PlayerRoute()`: a `core::Journey` of the cultivator alone with one leg by `core::WALKING`, `core::FindRoute` from the foot's tile to the point's, set out from the foot itself on the clock's tick; ignored off the world map, off the map's tiles or towards a tile it can't reach, logged at debug; one to the tile it stands on ends any route where it stands): each tick its body is where `core::Where` puts the route at the clock, so it stands while the world is paused or the clock waits for a month step and moves on with M's jump; held movement ends the route, paused too, and walks freely unless paused; the route ends on its last tile at the leg's end; it is saved and hashed (`Host::Load` refuses one that isn't the player's single walkable leg on the world map), dropped when the scene is left, and published as `Snapshot::route` (the foot, then the centres of the tiles still to walk). On the world map the cultivator explores (`WorldState::explored`, one bit per tile, row by row, `core/fog.hpp`; `Host::ExploredTiles()`): every tile within the sight radius (`WorldState::sightRadius`, the game data's cultivator's `sight` in a new game; `Host::SetSightRadius`) of its foot's tile when the scene is built, after each tick's move (before the portal check) and after M's jump, and of each tile its route reaches in between, so none it passes stays unexplored; never by the view, the frame rate or the worker count (`Host::Explore` is for harnesses). A scratch world has neither (`Host::Load` refuses one with bits or sight, a game world whose bits don't fit its map, `core::FogBitsFit`, and any sight past `core::MAX_SIGHT`, the cap `creatures.yaml` is read against too); `Host::FogVersion()`, never saved or hashed, changes with the bits and at each scene entry. A scene with a cultivator to walk names its portal's point (`SceneTraits::portal`, or `Scene::Portal(context)` for one that follows the game data, `SceneTraits::portalFromMap`: the world's, the start city's tile centre less (560, 200); none for `painted` and `cells`; `Host::Portal()` gives the running scene's): the host checks the player's foot against it in the tick (the path the foot takes crossing an ellipse `PORTAL_RADIUS` across, squashed by `PORTAL_DEPTH_RATIO` as the seal is drawn, so it records and replays as any walk) and asks for the next walkable scene (`NextWalkableScene`), and publishes it as scene content, the `portal` seal of `seals.yaml` (never a showcase seal) with a caption over it.
- A new module adds its directory's `module.dox`, an XMake target with `add_deps` on the modules below it, and its commit scope to `SCOPES` in tools/project_n.py.

## Commands
- `./dev run [--debug] [-- --stress | --painted | --cells | --world]` (native preset; `--preset` picks another; `--stress`: the stress arena, about 100,000 instances; `--painted`: the still painted test scene; `--cells`: a map cell grid, to judge the mips as the view zooms; `--world`: the world map, 20 screens across, of terrain tiles and the travellers between its cities (`game/scenes/world.hpp`); `--<name>` for each scene in `art/scenes.toml` the game knows; `--quit-after SECONDS`: quit by itself; `--zoom VALUE`: every scene starts at this zoom, from 0.25 (the farthest) to 2 (the closest), for `profile -- --cast-swords --zoom 2`; `--burst`: F7's burst once a second, for `profile -- --burst`; `--debug-sight`: the whole world map seen through the fog from the start (F3 flips it; the switch snaps the fade, explored tiles still ease in as they are explored, and the host's sight and explored tiles are untouched); `--cast-swords`: the flying swords beside the player 4 seconds after the last cast or as soon after as they are ready (about every 6 seconds), the fire bolt topping the Qi up first, for `profile -- --cast-swords`, with each cast's latency to its first drawn sword in the log file at debug level; `--workers N`: pin the job system to N workers, 1 to 64; `--unpaced`: present immediate before mailbox, so the display's rate doesn't cap a measurement; `--camera-path` (for `--world`): 2 seconds after the scene runs, the camera follows a fixed path (`app/camera_path.hpp`, which `app::CameraControl` moves by: follow the cultivator walking east by a scripted Move in steps of 0.5 s (standing 0.1 s, then walking 0.4 s: eight presses, each from a standing cultivator), pan 3 screens, zoom in to 2 and out to 0.25, the widest view over the busiest region, zoom 0.6 with labels) and the game quits after it, logging `camera path: <segment>` at each segment's start (also a Tracy message) and `input latency: <ms> ms from a Move press to its first drawn frame` for each press; `--travel-share PER_MILLE`: the world map's travel share (`world.yaml`'s `share_per_mille`) set to this, 0 to 1,000, before the game starts (`game::SetTravelShare`, so the data's hash follows it), for `measure`'s world run; `--month-step-at SECONDS` (with `--camera-path`): one month passes (`core::ActionKind::AdvanceCalendar`, as M sends it) at that second of the path, logging `camera path: month step` (also a Tracy message; `app::PathMonthStep`, `app::MonthStepAtOf`), for `measure`'s world run; `--fullscreen`: this run fullscreen at the display's native size, whatever `settings.yaml` says; the log names the display mode as `display: WxH at N Hz (name)`, again whenever the window lands on another display or its mode changes (a compositor may place a new window elsewhere than SDL opened it)). In the game (default bindings, `app/bindings.cpp`): WASD, the arrows, the d-pad or the left stick walk the cultivator (pan the still scenes; walking onto a scene's glowing portal goes to the next walkable scene: arena, stress, world, then the arena again), in the arena a left click casts the generator, a right click the spender, Space the movement and 1 to 5 the specials and ultimate (Alt and a left click selects; ## Gotchas
- A `///` comment right after the `/// @file` block joins it, leaving the next declaration undocumented: put a blank line after the file comment.
- SDL 3 silently falls back to XWayland when the compositor lacks `fifo-v1` (niri does), even with the Wayland driver compiled in. `platform/window.cpp` hints `wayland,x11`; `SDL_VIDEO_DRIVER` still overrides it.
- A `switch` over every value of an enum fails either way under Clang's `-Weverything`: `-Wswitch-default` wants a `default`, `-Wcovered-switch-default` rejects one. Use `if`s.
- A member that a designated initialiser can omit needs an initializer under Clang (`-Wmissing-designated-field-initializers`; it names one member per site): `{}` under `// NOLINTNEXTLINE(readability-redundant-member-init): designated initializers omit it; Clang warns without one`, or a value tidy accepts (`= nullptr`, `= std::nullopt`). Every other member with a default constructor stays bare.
- MSVC's warnings don't show in native Linux builds, only in the windows-msvc builds (each task's release build, `check`): `std::array` needs double braces (C5246). Deduced from scalars (`std::array KEYS{ InputCode::KeyW, ... }`) it warns too, and double braces then stop the deduction (C2641): write `std::to_array({ ... })`. Arrays of aggregates (`std::array CASES{ Case{ ... }, ... }`) pass.
- `std::ranges::find` over a `std::array`: clang-tidy wants `const auto*` (libc++'s iterator is a pointer), which MSVC rejects (its iterator is a class; only windows-msvc builds show it). Search a named `std::span` of the array instead and keep `const auto`, as `platform/window.cpp` does.
- Profiling is skewed by anything else animating on the GPU: a browser page with a moving canvas (the superpowers brainstorm companion's) made the same build's frames four to eight times slower (2026-11-12). Close animated pages and leave the game's window focused while `profile` runs; compare a build only with a baseline taken the same way.
- On the development machine (niri) `settings.yaml`'s window size isn't what a profile runs at: the window is tiled (1280×720 became 1256×1368), and fullscreen is paced at the monitor's 165 Hz despite mailbox, where every zone ran three to five times slower than unthrottled (2026-11-13). Record the size `niri msg windows` shows, and compare zones only between runs paced alike.
- `PN_PROFILE_MESSAGE` takes a `std::string` or `std::string_view`, never a bare literal (it calls `.data()`). The macros are empty outside `releasedbg`, so `test` and `lint` compile a wrong call, and only `check`'s releasedbg build or `measure` fails on it: name the text as a `constexpr std::string_view`.
- A function called once per item, thousands of times a frame, takes no `PN_PROFILE_ZONE`; its caller's zone (or its job chunk's) measures it. Under a capture a zone costs its caller about 0.25 µs (measured 2026-11-11 as a parent zone's time less its children's), many times a small function's work: the damage numbers' nested zones were 2.3 of the 2.4 µs each number took to place.
- MSVC C4868 (only in windows-msvc builds): braces around constructor arguments that build a temporary with a destructor (a `std::filesystem::path` copied into a by-value parameter, a `std::move`d one). Use parentheses for such constructor calls.
- MSVC C4623 (only in windows-msvc builds): an aggregate holding a member with no default constructor (`core::State`) warns that its own default constructor is implicitly deleted. Give it a constructor (`game/host.hpp`'s `Loaded` takes every member, `game/world_state.hpp`'s `WorldState` its `core::State`).
- MSVC C4686 (only in windows-msvc builds): a function declared returning a `std::array<...>` that nothing has instantiated by then warns at its first call. Name the type (`using Table = std::array<...>`) and `static_assert(sizeof(Table) == ...)` it before the declaration (`gfx/glow_table.hpp`).
