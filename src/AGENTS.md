# src/: game and engine

## Scope
All game and engine code, structured by docs/design/0002-engine-architecture.md (phases 1 to 5 of §16 implemented). Modules are XMake static libraries in `src/<module>/` (`core`, `data`, `platform`, `gfx`, `game`, `app` so far; `data` reads the YAML files, settings and data tables, into core's types, and only it sees yaml-cpp); each links and includes only the modules below it (`MODULES` in tools/project_n.py; `lint` checks the includes), and `game` links only `core`. `app` puts the program together (0002.1): `app::App` owns the job system and the main thread's systems (window, renderer, display, damage numbers) and runs the main loop; it starts the logic thread, which registers with the job system (only the creating thread and registered ones fork) and builds an `app::Game` owning that thread's systems (saves, `game::Arena` through `core::Simulation`, `core::Logic`, the tick clock). The threads share only `core::GameHandover` (`core/frame.hpp`). Scenes load on demand (0002.3.1): each snapshot names the scene its state needs; App has the renderer decode and upload its sprites a little each frame, then sends `SceneResident`, and until then the logic's bursts wait, running no tick. `main.cpp` only parses the command line, reads the settings (`settings.yaml` in the per-user data folder: window size, fullscreen, language, text and damage number options; `core/settings.hpp`), the atlas manifest, the game data and the strings table, opens the window and renderer (with the text options and the table of UI colours, `core::UiColours`: every UI colour lives there, none in code or shaders), and runs an `App`. A new system is owned by `App` or `Game`, never passed in as loose arguments.

## Rules
- C++23 with conventional headers (no modules). Every translation unit's includes lead to `core/cxx23.hpp`, which fails the build below C++23; include it with `// IWYU pragma: keep` (it declares nothing).
- Include order: project headers, then library headers (`<SDL3/...>`), then (headers only) the standard library, as blank-line-separated blocks. clang-format sorts within a block but doesn't regroup.
- Formatting and lint come from the pinned tools: `pixi run project_n fmt` and `pixi run project_n lint` (warnings are errors).
- Headers include only the standard library and our own headers. Third-party and platform code (SDL, Tracy, `<windows.h>`) stays in `.cpp` files behind our own types (a pimpl or an opaque handle); a header doesn't forward-declare its types either. `lint` fails on a third-party include in a header; only a facade (`FACADES` in tools/project_n.py) includes its own library, and a module's private `src/<module>/internal/` headers its libraries (nothing outside the module includes them).
- Numbers use the sized types from `core/types.hpp`: `i8`–`i64`, `u8`–`u64`, `f32`, `f64`, never `int`, `unsigned`, `long`, `float`, `double` or `std::uint32_t`-style names (`int main(int, char**)` excepted; `std::size_t` stays for sizes and indices; `lint` fails on the others). `pch.hpp` includes it; headers include it themselves.
- `pch.hpp` is the game's precompiled header and holds every standard header the sources use: a `.cpp` never includes a standard header itself (`lint` fails on one); add it to `pch.hpp`. Headers still include everything they use. It is a header too: no third-party ones.
- Logging: extensive, through `core/log.hpp` (Quill; `std::format` syntax, written on a background thread). Log outcomes (what was chosen, what happened, what failed and why), never code steps or internals, and never every frame (profile instead). `main` calls `core::log::Start(directory)` first; logs go to the console (Info and up) and to a rotating `project_n.log` in the per-user data folder. Nothing else writes output (`std::print`, iostreams, `printf`, `SDL_Log`) and nothing else includes Quill or Tracy: `lint` fails on them. Levels:
  - `PN_LOG_DEBUG` detail for diagnosing (decisions, state changes, values; log file only)
  - `PN_LOG_INFO` progress in a normal run (subsystems starting and stopping, what was chosen)
  - `PN_LOG_NOTICE` significant normal events (start, stop)
  - `PN_LOG_WARNING` unexpected but recovered · `PN_LOG_ERROR` a failure and its cause · `PN_LOG_CRITICAL` a failure the program can't continue after
- Profiling: `PN_PROFILE_ZONE();` at the top of every function that runs each frame (except per-item functions: Gotchas), `PN_PROFILE_FRAME();` once per frame, from `core/profile.hpp` (Tracy). They collect only in `releasedbg` and do nothing elsewhere: `./dev profile [--seconds N] [-- --stress]` records a run into `build/profiles/` (the game quits by itself with `--quit-after N`, so no click into the viewer takes its focus and pauses it), `./dev profiler <file>` opens it; or live, `./dev run --mode releasedbg` and `./dev profiler`.
- Every header starts with a `/// @file` comment followed by `/// @ingroup <module>` (the group is in `src/<module>/module.dox`), and every public class, function, member, variable and enum it declares has a Doxygen comment (`///`): what it does and promises, not how. `lint` fails on a missing or broken one.
- Errors: an expected failure returns `std::expected<T, core::Error>` (`core/error.hpp`); a broken invariant is `PN_ASSERT(condition, message)` (`core/assert.hpp`: on in debug and releasedbg). Our code throws nothing.
- Entities: EnTT only through `core/ecs.hpp` (a facade; `core::Domain`, `core::Registry`). Anything that crosses a domain, a tick, a save or input names an entity by its `core::StableId`, never an EnTT handle; structural changes (create, destroy) never happen inside a job chunk.
- Simulation code (`core`, `game`) is deterministic within one binary (design doc 0002 §7.4): transcendental maths through `core/math.hpp` (`lint` fails on `std::sin` and the like there), random numbers through `core/random.hpp` keyed on the state counter, never `std::*_distribution`, never a clock.
- Comments in `.cpp` files only explain why, or a complexity the code can't show; never restate what the code does.
- Unity builds are configured but off (`unity_build` in xmake.lua); `check` builds and tests the native preset with them once to keep them working. They put several sources in one translation unit, so keep names in anonymous namespaces unique across files (test files stay out of the batches: doctest's names would clash).
- Rendering: the world pass draws the snapshot's sprites, the outlines, the swords' trails (additive ribbons), the overlay (sprites the main thread places each frame at the render time: the swords' tinted cores, their additive halos, the poison lance's additive bursts, the health bars, which follow their creature's label, then the swords; `gfx/volley_draw.hpp`), then text, then the HUD in target pixels (`app/hud.hpp` lays it out: its bars through the overlay's sprites, then its lines). Nothing outside `gfx` calls SDL_GPU. Shaders are HLSL in `shaders/<name>.<stage>.hlsl`; after changing one, `./dev shaders` (Linux or Windows) and commit `shaders/bin/` and `src/gfx/generated/` with it (`lint` fails on stale binaries). `gfx` reaches them through the generated `gfx/generated/shaders.hpp`.
- Third-party code comes from xmake-repo packages with exact versions; nothing is vendored into `src/`.
- `src/<module>/generated/` holds headers that `shaders` and `atlas` write (shader binaries, the sprite names; the atlas manifest itself is `assets/manifest.yaml`, which `main` loads into `core::Manifest`): never edit them by hand; `fmt` and `lint` skip them, and `lint` fails when they are stale.
- The arena (`game/arena.hpp`) is the growing demo scene: a new feature of the game or engine shows up in it, in the same branch, and is added to the header's list.
- A new module adds its directory's `module.dox`, an XMake target with `add_deps` on the modules below it, and its commit scope to `SCOPES` in tools/project_n.py.

## Commands
- `./dev run [--debug] [-- --stress | --painted | --cells]` (native preset; `--preset` picks another; `--stress`: the stress arena, about 100,000 instances; `--painted`: the still painted test scene; `--cells`: a map cell grid, to judge the mips as the view zooms; `--<name>` for each scene in `art/scenes.toml` the game knows; `--quit-after SECONDS`: quit by itself; `--burst`: F7's burst once a second, for `profile -- --burst`). In the game (default bindings, `app/bindings.cpp`): WASD, the arrows or the left stick walk the cultivator (pan the still scenes), in the arena a left click casts the generator, a right click the spender, Space the movement and 1 to 5 the specials and ultimate (Alt and a left click selects; elsewhere a left click selects), the wheel or the shoulder buttons zoom, Escape quits; debug keys: F2 switches to the next scene (arena, stress, painted, cells), M lets a month pass, F5 saves, F9 loads, F6 starts or finishes recording a replay, F10 plays or stops it, F7 hits every fox thousands of times (the damage numbers' stress); saves and the replay go to the per-user data folder's `saves/`. Debug builds reload `assets/data/` (the source tree's) within half a second of an edit; a broken edit is logged with its line and the old data stays

## Gotchas
- A `///` comment right after the `/// @file` block joins it, leaving the next declaration undocumented: put a blank line after the file comment.
- SDL 3 silently falls back to XWayland when the compositor lacks `fifo-v1` (niri does), even with the Wayland driver compiled in. `platform/window.cpp` hints `wayland,x11`; `SDL_VIDEO_DRIVER` still overrides it.
- A `switch` over every value of an enum fails either way under Clang's `-Weverything`: `-Wswitch-default` wants a `default`, `-Wcovered-switch-default` rejects one. Use `if`s.
- A member whose type's default constructor is defaulted (`std::unordered_map`, EnTT's registry, `core::Mutex`): GCC's `-Weffc++` demands an initializer, clang-tidy calls `{}` redundant. Keep `{}` with `// NOLINT(readability-redundant-member-init): GCC's -Weffc++ requires an initializer`, or use a value tidy accepts (`= std::nullopt`).
- MSVC's warnings don't show in native Linux builds, only in `check`: `std::array` needs double braces (C5246), also with CTAD.
- `std::ranges::find` over a `std::array`: clang-tidy wants `const auto*` (libc++'s iterator is a pointer), which MSVC rejects (its iterator is a class; only in `check`). Search a named `std::span` of the array instead and keep `const auto`, as `platform/window.cpp` does.
- A function called once per item, thousands of times a frame, takes no `PN_PROFILE_ZONE`; its caller's zone (or its job chunk's) measures it. Under a capture a zone costs its caller about 0.25 µs (measured 2026-11-11 as a parent zone's time less its children's), many times a small function's work: the damage numbers' nested zones were 2.3 of the 2.4 µs each number took to place.
- MSVC C4868 (only in `check`): braces around constructor arguments that build a temporary with a destructor (a `std::filesystem::path` copied into a by-value parameter, a `std::move`d one). Use parentheses for such constructor calls.
