## 1. What phase 4 asks

"Replay of an input log, frozen ticks included, reproducing the same state hashes" (§16). §7.4: a recording
starts from a saved state, canonical at that moment; it logs the effective input of every wall tick plus a
hash of the state every 60 wall ticks, so a divergence is caught within a second of starting; starting a
replay is a new timeline epoch. Same binary only; across builds nothing is promised.

## 2. A determinism fix first: burst boundaries must not matter

Today a calendar request mid-burst freezes the burst's remaining ticks, and the transition is published at
the burst's end, so **the wall tick the step runs at depends on where the clock split the bursts**: a
scheduling accident. Nothing keys on the wall tick yet, but a replay logged per wall tick would drift.

**Change:** a tick that takes AdvanceCalendar **ends its burst** (as Save and Load already do), publishing
the transition at once; the step runs on the very next wall tick. Every state transition then sits at a
fixed wall tick after its input, whatever the burst sizes, and a replay can feed input by wall tick alone.
The burst's remaining ticks (at most two, MAX_CATCH_UP − 1) aren't run: the game is frozen behind the
transition anyway, and the wall counter counts only ticks run. The clock isn't restarted for it (not a
stall). One logic test changes with it (the frozen-burst case now ends after its first tick).

## 3. Ownership (0002.1's rules)

```
app::Game                    logic thread
├── core::Saves  saves       the save slot (as now)
├── core::Saves  replays     a second slot: the replay file (Saves stores bytes; it doesn't care what they are)
├── core::Replay replay      recording or playing, or neither; the log in memory
└── core::Logic              holds &replay like &saves; asks it for input and hands it hashes
```

**`core::Replay`** (`core/replay.hpp`): no I/O, no threads; a recording is bytes in memory.
- `StartRecording(std::vector<std::byte> start)`: the bytes Logic serialised at that tick become the
  recording's start: its own state (paused, the calendar step's phase), then what a save holds (the tick
  counters and the simulation's state, sorted, so canonical at that tick). The counters travel inside these
  bytes; Replay never reads them.
- `Record(std::span<const Action>)` once per wall tick, in order (at most 255 actions a tick; more are
  dropped with a warning); `RecordHash(u64 wallTick, u64 hash)`.
- `std::vector<std::byte> FinishRecording()`: the whole log, for `replays.Write()`.
- `StartPlaying(std::vector<std::byte>)` → the start state's bytes, or an error (malformed, another format,
  another version of the game); then `Next()` → the next recorded tick's actions until `AtEnd()`,
  `CheckHash(u64 wallTick, u64 hash)` → match, divergence, or nothing recorded there; `Matched()` and
  `HashCount()` count the checks; `StopPlaying()`.

**`core::Logic`** decides when, as with saves:
- New actions: `ToggleRecording` and `PlayReplay` (shortcut keys F6 and F10 until bindings in phase 5).
- **Recording:** a tick that takes ToggleRecording (frozen, ends its burst) serialises the state into the
  replay as its start; every later tick records the actions it took (an empty tick costs one byte); every
  60th wall tick records `Logic::Hash()` (the counters, pausing, the calendar phase and
  `simulation.StateHash()`). ToggleRecording again finishes it, as do a Load (which starts a new timeline)
  and PlayReplay (which then plays what was just recorded), and `replays.Write()` writes it on the
  background job.
- **Playing:** a tick that takes PlayReplay reads the replay (`replays.Read()`), restores its start state as
  a load does (new epoch), and from then on takes its input from the replay, not the handover. Live input is
  still drained so the queue can't grow, and dropped (a ToggleRecording or Load included), except
  PlayReplay, which stops playback. Each 60th wall tick checks the hash. A **divergence is logged as an error
  with its wall tick, and playback stops**; the game goes on live from there (a bug report keeps the log line
  and the file). After the last recorded tick playback stops by itself and live input resumes; the log line
  gives the reason and the checks matched ("replay stopped at tick T because it finished; N hash checks
  matched"). A replay file holding an action that is never recorded (a Load, ToggleRecording, PlayReplay)
  is refused as malformed.
- A Save during recording is recorded as an action and replayed (its canonical sort is part of the
  timeline, §7.1), but a replayed Save writes no file.

## 4. The replay file

LZ4 and the checksum come from `core::WriteSaveFile` (the same container as saves). Inside:

```
u32 replay format · game version string (u8 length + bytes)
start state: u64 byte count + the bytes above (Logic's state, then what a save holds, whose own
             save format leads the save's part)
ticks:       u64 count, then per wall tick from the start: u8 action count, then each action's kind (u8)
hashes:      u64 count, then (u64 wall tick, u64 hash) pairs
```

The version string (from `set_version` in xmake.lua, passed in as a define) refuses a replay from another
release with a clear message; two builds of one version that differ are caught by the first hash check
instead. Ten minutes of play is 36,000 ticks: about 36 KB of input before compression.

## 5. Testing

- `core_tests` (`Replay`, with a fake simulation): a recording plays back the same actions at the same wall
  ticks; hashes match; a tampered hash is reported as a divergence at its tick; a malformed or truncated log
  is refused.
- `core_tests` (`Logic`): the calendar request ends its burst and the step runs on the next wall tick,
  whatever the burst sizes (the same inputs under bursts of 1 and of 3 give the same counters and steps).
- `game_tests` (the phase 4 gate): the stress arena recorded over a few hundred ticks with pauses, a month
  step and a save in them, then played back in a fresh `Logic` and arena: every hash matches and the final
  state hash equals the recording's. And a deliberately changed state diverges at the next 60-tick check.
- `app_tests`: F6/F10 are App's keys, not unit-tested (as F5/F9).

## 6. Not in this piece

- Seeking, speeding up or rewinding a replay; several replay slots; a replay screen (UI, phase 6).
- Replays across builds or platforms (§7.4 says nobody asked).
- Writing a recording that is still under way when the game closes: it is lost; F6 finishes and writes it.
