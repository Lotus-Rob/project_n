## 1. Problem

Phase 4's first save and load put the save slot, the file writing and its logging inside `core::Logic`, and
`main.cpp` passed loose arguments into the logic thread's entry function (the handover, the start time, the
scene, the save path, a failure flag), building the job system, the clock, the logic and the arena as locals
there. Every new system would have meant another parameter threaded through, and `Logic` was doing two jobs:
driving ticks and storing saves. The user asked for systems held by a Game or an App instead (2026-11-06).

## 2. Ownership

```
main()                       parses arguments, opens the window and renderer, reports start-up failures
└── app::App                 main thread: window, renderer, handover, display, camera, events
    └── std::jthread         the logic thread; its body builds:
        └── app::Game        logic thread: jobs → saves → arena → logic → clock (built in that order)
```

- **`Game` is built on the logic thread**, inside the jthread's body, not by `App`: enkiTS lets only the
  thread that creates the job system fork (§7.5), so `Jobs`, and with it everything that forks, must be
  created there. `App` holds the jthread as its last member, so the logic thread stops and joins before the
  handover it uses is destroyed.
- **Systems hold their collaborators, set once.** `core::Logic(GameHandover&, Simulation&, Jobs&, Saves&,
  u64 (*now)())` keeps them as non-owning pointers, and `RunBurst(burst, stop)` takes only what changes per
  call. Passing references per call was never a speed problem; the gain is one owner per system and call
  sites that don't grow with each new one.
- **A new system is owned by `App` (main thread) or `Game` (logic thread)**, never passed in as loose
  arguments (src/AGENTS.md).

## 3. The pieces

- **`core::Saves`** (`core/saves.hpp`): one save slot. `Saves(slot, Jobs&)`; `Write(bytes)` writes on the
  job system's background job and logs the outcome; `Read()` waits for a write in progress, then reads and
  validates the file (`core::ReadSaveFile`). An empty slot (no folder for saves) refuses both with a
  warning. `Logic` only decides when to save or load and what goes in: its tick counters, then the
  simulation's state (§7.6).
- **`app::Game`** (`app/game.hpp`): owns the logic thread's systems. `Step(nowNs, stop)` runs one round of
  the loop: advance the clock, log overload changes, run the burst, restart the clock after an expected
  stall (a calendar step, a save, a load). `Run(stop)` waits for each tick and `Step`s. `Step` takes the
  time, so tests drive it with a fake clock and no waiting.
- **`app::App`** (`app/app.hpp`): owns the main thread's systems and the logic thread. `Run()` is the main
  loop (poll, quit checks, input to actions, events, display, present, the transition's frame cap).
- **The `app` module** sits above every other module, the only one that may use them all (`MODULES` in
  tools/project_n.py); `project_n` links only it.

## 4. Testing

- `core_tests`: `Saves` (a round trip through the background job, the last write wins, refusal with no
  slot); the logic tests build `Logic` with its collaborators in one rig.
- `app_tests`: `Game::Step` on the arena at chosen times: a step publishes its tick's snapshot, and after a
  calendar step the clock restarts when the step ended instead of catching up.
- `App` needs a window and isn't unit-tested, as `main` wasn't.

## 5. Left as it was

- The headless benchmark drives `game::Arena` directly: it measures the simulation, not the threads.
