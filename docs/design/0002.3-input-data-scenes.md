## 1. What phase 5 asks

"Bindings and actions with latching across bursts, gamepads and prompts, picking against the displayed frame, the
camera on the main thread; the manifest; the scene-loading protocol with decoding on workers as low-priority jobs;
the `data` module with YAML settings and one data table; hot reload of data in debug builds" (§16).

It lands as one branch, `phase5-input-data-scenes`, in three chunks, each a series of commits that passes `check`:

1. **Input and camera** (§3, §4): bindings, actions with arguments, held input, gamepads, prompts, picking, the camera
   following the player. Replaces the F-key and M shortcuts.
2. **The `data` module** (§7): yaml-cpp, the settings file, one data table, hot reload. Second because chunk 3's
   manifest is YAML too.
3. **The manifest and scene loading** (§5, §6): the loaded manifest replaces the compiled atlas metadata; scenes load
   through §9's protocol with decoding on workers; phase 4's frozen-tick load moves behind it.

## 2. Something to steer with

Nothing in the arena takes input today, so bindings would have nothing to drive. **The cultivator becomes the
player's:** it walks with WASD, the arrow keys or the left stick, the camera follows it (§8.10: "in combat it follows
the interpolated position of the entity the snapshot names"), and the logic culls around it. A left click on any
creature selects it; the arena outlines the selected one in gold (first a tint, §3) and logs the choice. In the cell grid the camera pans
with the same movement input and zooms with the wheel, as now. This is a test bed, not gameplay: the gameplay doc
replaces it.

**The arena is the growing demo scene** (the user, 2026-11-07): it shows every feature of the game and engine, and
each new feature adds itself there (`game/arena.hpp` lists them). Before chunk 3 it gained the painted art (some
drawn larger or smaller, the ice crystal turning through a new saved `Spin` component), a gold glow, and the NPCs:
six walking in the active tier and 5,000 in the world tier, so M's month step runs on something. The test-only
`Npcs` scene, which existed for those NPCs, goes. The stress scene keeps its 50,000-strong world.

## 3. Input (chunk 1)

```
platform::Window::Poll   SDL events → WindowState (focus, visibility, quit) + a list of platform::InputEvent
app::Bindings            InputEvent → Control presses and releases, held axes        (App owns it; pure, tested)
app::App                 Controls → core::Action (the logic's) or App's own (quit, zoom); picking; HeldInput
core::GameHandover       input channel: Actions accumulate (as now); HeldInput is newest-wins (new)
core::Logic              presses to the first tick of a burst; HeldInput to every tick of it
```

- **`platform::InputEvent`** (`platform/window.hpp`): `{ device (Keyboard, Mouse, Gamepad), code, pressed, value,
  position }`, our own type so SDL stays in `window.cpp`. Key repeats are dropped there. Gamepads open on
  `SDL_EVENT_GAMEPAD_ADDED` and close on removal; `SDL_Gamepad`'s standard layout gives one set of codes for every
  controller. `WindowState` loses its five `*Requested` flags and `wheelNotches`.
- **`app::Bindings`** (`app/bindings.hpp`): a table from physical input to a **`Control`** (an app enum: `Move` as an
  axis pair, `Select`, `Zoom`, `Quit`, `AdvanceCalendar`, `Save`, `Load`, `ToggleRecording`, `PlayReplay`). Default
  bindings are code (§10): WASD and arrows, left stick (with a 0.2 radial dead zone) → Move; left click → Select;
  wheel and the shoulder buttons → Zoom; Escape → Quit; M, F5, F9, F6, F10 as now. Rebinding and saving it to the
  settings file stay later (§10). Debug keys get no gamepad binding.
- **Actions grow arguments.** `core::Action` becomes `{ kind, StableId target, std::shared_ptr<const GameData> data }`:
  `target` for the new `ActionKind::Select`, `data` for chunk 2's `ReloadData` (added with it), empty otherwise. Movement isn't an
  action: it is held state.
- **Held input and latching** (§10): `core::HeldInput { Vec2 move; }` goes through a new newest-wins slot in the
  handover (`SendHeld` / `ReadHeld`, under the same mutex; reading doesn't consume it). Each tick of a burst gets the newest held input; presses
  (actions) go once, to the burst's first tick, as now, so a press and release between two ticks still arrive as
  both. Later ticks of a catch-up burst repeat the held input, so movement doesn't stop. A movement tap shorter than
  a tick (16.7 ms) is missed; nothing needs one.
- **Prompts:** App remembers the device used last and, for a gamepad, its family from `SDL_GetGamepadType` (Xbox,
  PlayStation, Nintendo, other), through `platform`; a change is logged. Nothing draws a prompt until the UI
  (phase 6), which reads it from App.
- **Picking** (§10): `Snapshot` gains `ids`, a `std::vector<StableId>` parallel to `instances` (0 for an instance
  that isn't an entity: ground, shadows, bullets), refilled in place like `instances`. A click's window position goes
  through the inverse of the camera transform (`gfx::ClipToWorld`, pure and tested) to a world point; App walks the
  drawn snapshot's instances from the top of the drawing order down and takes the first with an ID whose quad, at
  the frame's alpha, contains the point. The action carries that ID, so a click on a moving fox hits the fox the
  player saw. The point is turned back by the instance's interpolated rotation, so a turned sprite is hit where it is
  drawn (the user, 2026-11-07, once the arena's crystal turned); transparent pixels count as hits, a shortcut.
- **Hover outline** (the user, 2026-11-07): each frame App picks at the mouse cursor (`Window::Cursor`, none while a
  gamepad is in use) with the frame's own alpha and passes the instance's index to `Renderer::Draw`. After the scene
  the renderer draws that instance once more from the uploaded buffer, its quad grown by the ring, with the outline
  set in the draw's uniforms (no instance format change, nothing uploaded per frame): the fragment shader colours the
  transparent texels within three texels of the sprite's coverage pale white, over everything, so a hovered fox
  behind a pine still shows. The selection is outlined the same way in gold (the user, 2026-11-07, replacing its
  tint): the arena publishes the selected instance's index in `Snapshot::selected`, and the gold wins where both
  fall on one entity. The stress arena's 100,000 IDs are 800 KB more written per publish,
  inside the pack's chunks; the benchmark gate shows whether that matters.

## 4. The camera (chunk 1)

- App owns `gfx::Camera`, as now. In a scene with a follow target, `Snapshot::follow` carries the target's foot at
  the previous and current tick, and the camera centres on it interpolated by the frame's alpha, so it moves as
  smoothly as the sprite. Without one (the cell grid), held movement pans it at the frame rate, by elapsed time.
  Zoom works everywhere, inside `MIN_ZOOM`..`MAX_ZOOM`.
- The logic culls around the follow target with a margin for the widest window and the smallest zoom (§7.2), so
  App needn't send its view back. The world map's view rectangle as input (§8.10) waits for the world map.

## 5. The job system moves to App (revises 0002.1 §2)

§9 has the **main thread** request scene decodes on the workers. Today `Game` creates `core::Jobs` on the logic
thread because only the creating thread could fork, and App never sees it. enkiTS (v1.12, `TaskScheduler.h`) lets
**registered external threads** add tasks and wait on them (`numExternalTaskThreads`, `RegisterExternalTaskThread`).

**Change:** App creates `Jobs` on the main thread, a member before the logic thread, with one external thread slot;
the logic thread registers itself when it starts (in `RunLogic`, before building `Game`) and deregisters at the end.
`Game` takes `Jobs&` instead of owning it. The forking rule becomes: the creating thread and the one registered
thread may start work and wait on it; ParallelFor still joins only on high-priority work. Tests that build `Jobs` on
their own thread are unaffected.

`Jobs` gains **`Start(chunks, body) → Pending`**: low-priority chunks that return at once; `Pending::Done()` polls and
its destructor waits. `Background` stays for the single save write.

## 6. The manifest and scene loading (chunk 3)

### The manifest

- `./dev atlas` writes **`assets/manifest.yaml`**: the page size, page count and mip levels; per sprite (in
  `art/sprites.toml` order, its stable ID) its name, file, page, region and foot; per scene its name and sprites.
  Scenes come from a new `art/scenes.toml` (scene name → sprite names; `atlas` checks every name exists).
- The generated header shrinks to the `SpriteId` names (code still names sprites) and the list of names.
  `art/atlas.sha256` and lint's staleness check cover the YAML too.
- **`core::Manifest`** (`core/manifest.hpp`): plain structs. `data::LoadManifest(path)` parses it and refuses a
  manifest whose sprite names differ from the header's ("the atlas is stale: `./dev atlas`"). `main` loads it before
  anything starts (A14) and hands `std::shared_ptr<const Manifest>` to App, which gives it to the renderer and to
  Game, and Game to the arena; `core::atlas`'s metadata reads (the draw list, the sprite array) switch to it.
  Manifest hot reload isn't phase 5's (§16 says data).

### The protocol (§9)

- **`core::SceneId`**: a scene's index in the manifest. `Simulation` gains `Scene() → SceneId`, the scene its state
  needs; the arena maps `game::Scene` to a manifest scene by name when it is built or loaded.
- `Snapshot` gains `scene`. **The logic holds `m_resident`**, the scene the main thread last reported resident (none
  at start). While `simulation.Scene() != m_resident`, a burst **runs no tick** (no counter moves, nothing is
  recorded), takes input for a `SceneResident` action (Pause and Resume still count; any other action is dropped
  with a debug line), and publishes a frozen snapshot naming the scene. The burst that takes `SceneResident` for the
  needed scene ends on a stall, so the clock restarts instead of catching up.
- **Why no ticks:** loading takes a different wall time on every machine and run. Counting its ticks would put
  every later input at a different wall tick, and replays feed input by wall tick (0002.2 §2). With none counted, a
  load in the middle of a recording or a replay costs no determinism.
- **The main thread:** when the drawn snapshot names a scene the renderer doesn't hold, App starts it:
  `Renderer::BeginScene(scene, jobs)` has the scene's sprites decoded on the workers (`Jobs::Start`, low priority,
  one sprite per chunk, each into its own slot); each frame `Renderer::ContinueScene(budgetNs)` uploads decoded
  sprites (premultiplied, into their page's layer) until 2 ms of the frame is spent, then generates the mips once
  all are in and returns true; App sends `SceneResident{ scene }`. Meanwhile frames draw the clear colour
  (shortcut: the loading screen's view model and picture come with the UI, phase 6). The window never freezes.
- **Who triggers it:** the start (the arena is built for a scene, nothing is resident yet), a save loaded from
  another scene, and a replay that starts in another scene. Phase 4's frozen-tick load is therefore behind the
  protocol: a load restores the state; if its scene differs, the next bursts wait for it. `Renderer::Create` no
  longer loads sprites; it allocates the texture array for every page.
- **Memory:** the array keeps one layer per page and a scene fills only its pages; leaving a scene frees nothing.
  shortcut: memory for every page; per-scene arrays with a page-to-layer map once pages outgrow §13's budget.
- Small on-demand assets (portraits, sounds) and residency hints wait for what uses them (phases 6 and 7).

**As built** (the details and every departure: [0002.3.1](0002.3.1-manifest-and-scene-loading.md), §8 and its
"as built" notes): the names are compared, not hashed; a scene's uploads start once all its decodes are done; a
sprite already in the array isn't loaded again; `game::CheckScenes` refuses to start (or to hot-reload data) when a
scene with creatures doesn't load their sprites; a tick that changes the scene (F2) ends its burst.

## 7. The `data` module (chunk 2)

- **yaml-cpp 0.9.0** (MIT) through the add-dependency skill, private to `data` (a facade only `src/data/*.cpp`
  includes). Its exceptions are caught in `data`'s parse functions, which return `std::expected` (§9); nothing else
  sees one. `data` links `core`; `app` links `data`; `game` still links only `core`.
- **Unknown keys** (a typo such as `widht:`) are ignored but logged as warnings naming the file, line and key, so a
  typo doesn't silently keep a default (the user, 2026-11-07). The `Parse*` functions collect them for tests.
- **Settings** (`core::Settings`, `data::LoadSettings` / `SaveSettings`): `settings.yaml` in the per-user data folder
  with the window's size and whether it is fullscreen. Missing: the defaults are used and written out, so a player
  finds a file to edit. Malformed: a warning naming the line, and the defaults (the file is left alone). Read in
  `main` before the window opens.
- **One data table:** `assets/data/creatures.yaml`, the test bed's creatures (§2): per kind its sprite (by name, checked
  against the manifest in chunk 3), walking speed and orbit parameters, replacing the arena's constants for the
  cultivator and the foxes. `core::GameData` holds it; `main` loads it with the manifest; Game gives it to the arena.
  As built (chunk 2): `core::GameData` holds only scalars, the sprite already resolved to its ID (against the
  compiled atlas until chunk 3's manifest), so it hashes like any archived value. A saved `game::Creature` component
  marks which kind an entity is, so a reload can find the foxes. `game::BuiltInData()` repeats the shipped table for
  tests and tools that read no files. A kind's `orbit` is optional (the cultivator has none). An orbit's `around: player` makes it circle the player wherever it walks rather than its starting point
  (the user, 2026-11-07); the foxes ship with it.
- **Hot reload (debug builds only):** App checks the data files' modification times twice a second; on a change it
  parses them on the main thread (small files; a worker when they aren't) and sends `ReloadData` with the new
  `shared_ptr<const GameData>`. A parse failure is logged and the old data stays. The logic swaps it in at the tick
  that takes the action (`Simulation::SetData`), which ends its burst; a recording in progress finishes there ("the
  data changed") and a replay playing stops, as a load does. The arena reads speeds at every tick, so the change
  shows at once.
  As built: debug builds read and watch the source tree's `assets/data/` (`PN_SOURCE_DATA`), as the copy beside the
  binary is replaced at every build; the reload tick is frozen, like a save's. The arena gives existing creatures
  their kind's new sprite and orbit at once (a fox may jump to its new circle).

## 8. Determinism and the replay format

- Replays record each tick's **effective input** (§10): its actions with their arguments (`Select`'s target), and
  the held input when it changed since the tick before (a flag byte, then the two floats). `ReloadData` and
  `SceneResident` are never recorded; a replay file holding one is refused as malformed, like a Load.
- The start state gains a **hash of the game data**: playing a replay under other data is refused with a clear
  message (§7.6: "the replay log records the data's hash"). As built, the hash sits in the replay's header
  (format 3), beside the game version, so the refusal comes before the start state is read.
- The replay format and the save format both bump; no old files need reading yet.

## 9. Testing

- `platform`: none new (SDL events), as now.
- `app_tests`: `Bindings` from input events to controls (a key, the stick's dead zone, a press and release in one
  frame giving both); picking against a hand-built snapshot (the top instance wins, alpha moves the hit, an
  instance without an ID is skipped); the camera follows an interpolated target.
- `gfx` tests: `ClipToWorld` inverts `WorldToClip` at several sizes and zooms. The reference-picture tests load
  their scene through `BeginScene` and `ContinueScene` until resident.
- `core_tests`: the handover's held slot is newest-wins; Logic gives presses to the first tick and held input to
  every tick of a burst; a burst waiting for a scene counts no tick and the one that takes `SceneResident` ends on a
  stall; `Jobs::Start` runs every chunk while a ParallelFor at high priority never waits on it; a registered
  external thread forks and joins.
- `data_tests` (new): settings, creatures and the manifest parse; each malformed case (bad YAML, a missing field, a
  wrong type, an unknown sprite, a stale manifest) is an error with its line, never an exception.
- `game_tests`: the cultivator walks with held input; a replay with movement, selections, a save, a load into
  another scene and a month step plays back with every hash matching (phase 4's gate, extended); a replay under
  changed data is refused.

## 10. Tidied on the way

Cleaning up as each phase goes is the rule (the user, 2026-11-07); these land in the chunk that touches them.

- **Retired by the phase:** `WindowState`'s five `*Requested` flags and `wheelNotches`, their resets and key checks
  in `Poll`, and `App::SendInput`'s chain of `if`s (one lookup through the bindings) (chunk 1); the fixed-camera
  shortcuts in `app.hpp` and `arena.cpp` (chunk 1); `core::atlas`'s metadata in its twelve users, the header keeping
  only the names, with data's `SpriteNamed` shortcut (chunk 3); sprite loading inside `Renderer::Create`, now split
  into creating the array, decoding, uploading one sprite and generating the mips (chunk 3). Phase 4's frozen-tick
  load in `Logic` stays: it restores the state, and the protocol waits for the scene (0002.3.1 §4).
- **One `core::NS_PER_MS`** beside `NS_PER_SECOND`, for the two copies in `app` that a unity build clashed on
  (chunk 3).
- **The fuzz smoke test goes:** `tests/fuzz/smoke.cpp` is replaced by real targets: the save and replay readers
  (chunk 1, with the replay format change) and `data`'s YAML parsers (chunks 2 and 3).
- **`Game`'s constructor takes one struct** (`app::GameSetup`: the scene, the slots, the manifest, the data, the
  start time, the clock) instead of a growing list of arguments, as `app::Options` does for App (chunk 1).
- **`Logic::Requests` goes:** its four bools grow with every action kind and phase 5 adds three. A tick's actions are
  handled in one pass with a small flag set keyed by `ActionKind` (chunk 1).
- **`main.cpp`'s scene flags** come from the manifest's scene names once it exists, as F2 cycles
  through them (§12) (chunk 3).

## 11. Not in this piece

- Rebinding and saving bindings (§10 says later); drawing prompts, the loading screen and the transition (phase 6).
  Bindings become data then: a YAML table of defaults that the player's rebinds save over, refactored from
  `app/bindings.cpp`'s code table (the user, 2026-11-07).
- Culling relative to the window or the world's size instead of the fixed view around the player (`FOLLOW_HALF_VIEW`):
  to explore once a window shape or zoom outgrows it (the user, 2026-11-07).

- Hot reload of the manifest or of images; on-demand small assets; residency hints.
- The world map's camera and view rectangle.

## 12. Decisions (the user, 2026-11-07)

Accepted as proposed:
1. **The test bed (§2):** the cultivator under the player's control, the camera following it, click-to-select tinting.
2. **Jobs move to App (§5),** revising 0002.1: the logic thread registers with enkiTS as its external thread.
3. **Settings (§7):** window size and fullscreen only for now.
4. **The data table (§7):** creatures (sprite, speed, orbit).
5. **A debug key to switch scenes:** F2 cycles arena, stress, painted, cells; an action, recorded like any other, so
