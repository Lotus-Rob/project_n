### The font

- **Noto Sans SC** (SIL OFL 1.1, Simplified Chinese with Latin), Regular to start, Bold later for headings:
  upstream's region subset `NotoSansSC-Regular.otf` (notofonts/noto-cjk, `Sans/SubsetOTF/SC`, 8.3 MB a weight),
  committed whole through LFS into `assets/fonts/` by the `git-lfs` branch, its source and SHA-256 recorded in

## 4. The frame's passes (chunks 2, 3 and 6; chunk 2's in 0002.4.1)

Before phase 6 the world pass drew straight into the swapchain, which had to be `SDR_LINEAR`. Phase 6 builds
§8.4's frame up to what it needs, each part with its first user (0002.4.1 §1): the scene target and the composite in
chunk 2, the mesh path and batch textures in chunk 3, the blur passes in chunk 6:

```
copy pass     instances (when the snapshot changed), mesh vertices, UI geometry and textures, new glyphs
world pass    → scene target (R16G16B16A16_FLOAT): ground, world, effects, overhead (damage numbers), outlines
blur passes   → blur chain (half, quarter, eighth size, and back up): only while a modal is open (§9)
final pass    → swapchain: composite (scene or its blur; encode to the swapchain), then the UI in submission order
```

- **The scene target** is `R16G16B16A16_FLOAT` at the swapchain's pixel size times the render scale (1.0 for now),
  refitted when the acquired swapchain texture's size changes (0002.4.1 §2). The swapchain is always `SDR` and the
  final pass **encodes sRGB itself** (0002.4.1 §3, decision 2), so the renderer now starts on any window: the `renderer.cpp` shortcut goes. Low settings' 8-bit scene
  target and bloom stay later (bloom is in no phase yet; §13).
- **The mesh path** (chunk 3, 0002 §8.5): indexed triangles with position, UV and premultiplied colour, written by the main
  thread into a cycled vertex buffer per frame, with a static `u32` index buffer for quads built once. Text (§5) is its
  first user; DragonBones and strokes come in phase 7.
- **Batches gain a texture** (chunk 3; `core::Batch::texture`, an index into the renderer's bound textures: the scene's sprite
  array, the digit strip), resolving the `draw_list.hpp` shortcut. The instance format is unchanged.
- **New pipelines and shaders,** one file per stage (AGENTS.md): `mesh` (text and later meshes; R8 coverage or RGBA
  textures), `ui` (RmlUi's vertex layout, a transform, a texture or none, scissor), `composite` (scene to swapchain,
  with or without the blur, encoding sRGB; chunk 2), `blur` (chunk 6: downsample and upsample, a 13-tap filter each way,
  fragment passes only, as bloom will use). `mesh` comes with chunk 3, `ui` with chunk 4. `./dev shaders` commits them.
- **Reference pictures** stay the judge: today's pictures should come out of the scene target unchanged to within a
  rounding step; any that move get `reference --update` and a look. **As built** (chunk 2): all five stayed within the
  tolerance (most pixels within one level, the outline ring's edge within four), so none was updated. New pictures cover text, the blurred modal and a
  UI document (chunks 3, 6).

## 5. Text (chunk 3)

### `gfx`'s text API

SDL3_ttf, behind `gfx`'s public `gfx/text.hpp` (no SDL types):

- **`gfx::Fonts`** loads each font from `assets/fonts/` once, at sizes in whole pixels, with fallbacks
  (`TTF_AddFallbackFont`): Latin from the Noto Sans SC subset itself for now.
- **Shaping and layout** are SDL3_ttf's: `TTF_Text` with HarfBuzz, wrap width, alignment, and direction
  (`TTF_SetTextDirection`, `TTF_DIRECTION_TTB` for vertical Chinese).
- **Our own glyph cache, not SDL3_ttf's GPU text engine.** That engine uploads each new glyph on a command buffer it
  acquires and submits itself (`SDL_gpu_textengine.c`, `UpdateGPUTexture`), so a page of new CJK glyphs is hundreds of
  submits, and its atlases are GPU-only, which RmlUi's font engine can't use (§7). Instead **a custom
  `TTF_TextEngine`** (SDL3_ttf's documented extension point, `SDL_textengine.h`) receives each laid-out text's draw
  operations (glyph font, glyph index, destination rectangle); `gfx` rasterises missing glyphs on the CPU
  (`TTF_GetGlyphImageForIndex`), shelf-packs them into R8 atlas pages (2048², grown by page), and uploads the new
  ones in the frame's own copy pass. One cache serves game text and the UI.
- **Text from the logic is data** (0002 §8.6): `core::TextItem { font, string ID or number, colour, position,
  layer, direction }` in the snapshot, beside the instances. The main thread lays each out (cached by its content, so
  a label that doesn't change isn't laid out again) and draws it through the mesh path in its layer: world text sorted
  with the world by its foot, overhead text over it.
- **Strings** live in a table, `assets/data/strings.yaml`, read by the `data` module: an ID per string with its English
  and Simplified Chinese text. The language is a setting (`settings.yaml`, default English). RmlUi's documents
  translate through the same table (§7). See §14, decision 6.

### Tests

The glyph cache's packing and growth (pure, on fake glyph sizes); a missing glyph reported once; the strings table's
parsing and refusals (a duplicate ID, a missing language); a `TextItem` laid out to the same quads twice; a reference
picture of the arena's name label and vertical caption on lavapipe.

## 6. Damage numbers: the first events (chunk 3)

- **The digit strip:** at start-up `gfx` renders 0–9, `+`, `-` and `,` of the damage font, outlined
  (`TTF_SetFontOutline`), white, into a small texture: one strip per font and size. Numbers tint it per instance.
- **The first event kind.** `core::Event` gains a kind and a payload: `DamageNumber { position, value, colour
  index }`, cosmetic. The arena emits one per aura hit. The handover already stamps events with tick and epoch and
  drops stale cosmetic ones (0002 §5).
- **App plays them** at the render clock (the empty event player's shortcut goes): each starts a floating number that
  rises and fades over a second of render-clock time. Each frame App writes the live numbers as instances on the
  digit strip into a small per-frame buffer that the renderer draws in the overhead layer, after the snapshot's world.
  Hundreds a frame cost what sprites cost (0002 §8.6); none is a text object.
- **Tests:** the numbers' instances for a value (digits, separators, widths); a number's position and fade at a render
  tick; events of an old epoch never played.

## 7. The `ui` module (chunk 4; details in 0002.4.3)

0002 §4 already reserves it: `ui` depends on `core`, `gfx` and `platform`, and on RmlUi, privately.

- **S13 first:** RmlUi builds for all four presets; a document with Chinese and English text renders through our
  render interface; the roster scrolls smoothly (§8); and it **decides the font engine**:
  - **(a) Ours on `gfx`'s text** (proposed): a `Rml::FontEngineInterface` whose `GenerateString` lays text out with
    SDL3_ttf and returns meshes on the glyph cache's pages (as RmlUi `CallbackTexture`s, regenerated by bumping
    `GetVersion` when a page grows). UI and game text shape alike, fallbacks and HarfBuzz included. Needs the package
    override (§3).
  - **(b) RmlUi's FreeType engine,** no override and no code, but no shaping, a second glyph cache, and fonts loaded
    twice. Chinese renders (it needs no complex shaping), with `word-break: break-all` in the RCSS: RmlUi breaks lines
    only at white space (`ElementText.cpp`), so unbroken Chinese would overflow.
  - (c) RmlUi's HarfBuzz sample engine (`Samples/basic/harfbuzz`, MIT): shaping, but still a second cache and fonts.
- **The render interface** (`ui/internal/`) implements RmlUi 6's retained API on `gfx`'s public UI API
  (`gfx/ui_draw.hpp`: compiled geometry, textures, scissor, transforms). RmlUi calls it while rendering, but SDL_GPU
  can't upload inside a render pass, so `ui` **records** a UI draw list (new geometry and textures to upload, then
  draw commands in submission order) and the renderer replays it: uploads in the copy pass, draws in the final pass.
  RmlUi's own SDL_GPU backend works the same way (it records commands, then runs a copy pass before its render pass)
  and is our reference. Clip masks (stencil), layers and filters wait until a document needs them.
- **Input goes to the UI first** (0002 §10): App hands each `platform::InputEvent` to `Ui`, which maps it to RmlUi
  and says whether it was consumed (RmlUi's `Process*` calls return that); what isn't goes to the bindings as now.
  Gamepad navigation uses RmlUi's `nav-*` properties, with the d-pad and A/B mapped to arrow keys, Enter and Escape.
- **Documents** in `assets/ui/` (RML and RCSS), loaded through a file interface on our paths; hot reload in debug
  builds with the data folder's watch (0002.3 §7). RmlUi's debugger plugin opens on a debug key.
- **Scale:** RmlUi's density-independent pixel follows the window's height over the 1080 reference (0002 §8.10), so
  the UI grows with the window as the world does.
- **Main thread only.** The UI reads the drawn snapshot's views and sends decisions as actions (§8); it never touches
  the simulation, so determinism and replays are untouched.

## 8. View models and the NPC roster (chunk 5)

- **Subscriptions** (0002 §8.14): a new action, `ActionKind::Subscribe`, carries a `core::ViewRequest { kind, target,
  page }`; an `Unsubscribe` ends one. They change only what is published, never the state, so like `SceneResident`
  they're **never recorded** in a replay, and the state hash ignores them.
- **Views in the snapshot:** `Snapshot::views`, plain structs behind `shared_ptr<const>` with a version each, replaced
  only when their data changed (0002 §5: shared pointers are the only way large data crosses). Each view kind is a
  struct in the frame contract (`core/views.hpp`): **`NpcRoster`** (each world NPC's stable ID, cell, last action,
  power and needs: about 32 bytes a row, 160 KB for 5,000, rebuilt only after a calendar step) and **`NpcDetails`**
  (one NPC's fields and relationships, rebuilt when it changes).
- **The roster screen** sorts, filters (by action, by cell) and scrolls on the main thread over the view's rows. It
  is **virtualised**: RmlUi's `data-for` makes an element per item, so 5,000 rows would be 5,000 element trees; the
  data model exposes only the rows in view (plus a margin), and a spacer keeps the scroll bar true. Clicking a row
  subscribes to its `NpcDetails`.
- **Tests:** a subscription's view appears in the next snapshot and stops after unsubscribing; an unchanged view keeps
  its pointer (no copy); the roster's sort and filter over fixed rows; the virtual window for a scroll offset; a
  replay recorded with subscriptions plays back with the same hashes.

## 9. Screens: the pause menu, loading and the transition (chunk 6)

- **The pause menu** (§14, decision 3): Escape opens it and pauses the game (the `Pause` action), Escape or Resume
  closes it. It has Resume, Save, Load, Settings (§11) and Quit, so Escape no longer quits at once.
  It is **modal**: while it's open the scene is drawn blurred behind it (§4's blur passes).
- **Save slots:** Save and Load open a slot list (three slots, each showing its scene, play time and when it was
  saved), replacing `main.cpp`'s one-slot shortcut. F5 and F9 stay as debug keys on the first slot.
- **The loading screen:** while the drawn snapshot's scene isn't held, the final pass draws a loading document over
  the backdrop instead of the clear colour: the scene's name and a progress bar from `Renderer::ContinueScene`, which
  now reports sprites decoded and uploaded of the scene's total. The main thread knows it is loading, so this needs no
  view model from the logic (a departure from 0002 §9's "loading view model", recorded there).
- **The transition:** while `Snapshot::transition` is set, a transition document shows the month passing ("A month
  passes", the new month's number) over the blurred last frame, at the capped frame rate. The month comes from a
  small `Calendar` view the arena always publishes.

## 10. Prompts (chunk 6)

- App already knows the device used last and the gamepad's family (0002.3 §3). The UI shows **the glyph for a control
  on that device**: a keycap with the key's name for keyboard and mouse, and a button glyph per family (Xbox,
  PlayStation, Nintendo, generic) for gamepads, switched the moment another device is used.
- The glyph images are sprites in a UI atlas (placeholders from `art/placeholders.py` until drawn), named per family
  and button; the binding table says which input a control has on each device (rebinding would update it).
- An RmlUi custom element, `<prompt control="pause"/>`, draws the right glyph and updates when the device changes.

## 11. Rebinding and settings (chunk 7)

The user's call (2026-11-09): in this phase, as the UI branch's last chunk.

- **Bindings become data** (0002.3 §11): `assets/data/bindings.yaml` holds the default table, each control's inputs
  per device (keyboard and mouse, gamepad), read by the `data` module and checked like the other tables (an unknown
  control or input, one input bound to two controls of one context). `app/bindings.cpp`'s code table goes, and with
  it the `bindings.hpp` shortcut. Debug keys stay code, outside the table.
- **Rebinds save over the defaults:** the player's changes go into `settings.yaml` as a list of (control, device,
  input) overrides, so new defaults in a later version still arrive for controls the player never touched.
- **`platform` reads every input,** not only the ones the defaults use (the `window.hpp` shortcut): all keys by
  scancode, mouse buttons, and the gamepad's standard buttons and axes, each with a stable name for the YAML.
- **The settings screen** (from the pause menu): window size and fullscreen (applied at once, saved), language
  (English or Simplified Chinese, §5), and the bindings list: pick a control, press the new input (Escape cancels),
  a conflict asks to swap, and "reset to defaults". The prompts (§10) follow the new bindings at once.
- **Tests:** the bindings table's parsing and refusals; overrides applied over defaults and surviving a changed
  default; capturing an input for a control; a conflict swapped; settings written and read back.
